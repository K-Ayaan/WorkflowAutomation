# Exercise 8 – Hospital appointment booking (Camunda 8)

A parent booking process checks slot availability with a DMN decision, books the slot and calls a reusable
`send-notification` child process (a Telegram message via the REST Outbound Connector). An interrupting event
subprocess handles cancellations at any time. Everything runs locally in Docker and is tested with a Postman collection.

## Contents

| Path | What it is |
|---|---|
| `bpmn/send-notification.bpmn` | Child process: start → **Send Telegram message** (REST connector `io.camunda:http-json:1`) → end. Inputs `recipientId`, `messageText`; URL `{{secrets.TELEGRAM_API_BASE}}/bot{{secrets.TELEGRAM_BOT_TOKEN}}/sendMessage`, body `{chat_id: recipientId, text: messageText}`. Returns `notificationStatus`, `telegramMessageId`. |
| `dmn/slot_decision.dmn` | Decision `slot_decision`, hit policy **UNIQUE**, inputs `department` (string), `bookedCount` (number), outputs `slotStatus` (AVAILABLE/FULL) and `suggestedAction`. Capacities: Cardiology 10, Neurology 8, Orthopedics 12, others 15. |
| `bpmn/hospital-booking.bpmn` | Parent process (final version, **propagation off**, explicit mappings). |

## Parent process `hospital-booking`

```
Booking requested → Check slot (business rule task → slot_decision) → Slot status?
   AVAILABLE → Book slot (FEEL script) → Send confirmation (call send-notification) → Appointment time reached (timer) → Appointment completed
   FULL      → Send slot-full notice (call send-notification) → Booking rejected (slot full)

Event subprocess "Handle cancellation" (interrupting message start "booking-cancellation", correlation key = patientId)
   → Release slot (FEEL script, bookedCount − 1, bookingStatus = CANCELLED) → Send cancellation notice (call send-notification) → Booking cancelled
```

The timer after the confirmation keeps a booked instance alive until the appointment (`appointmentWaitTime`, default
`PT10M`), so a cancellation can arrive "while the booking is in progress". The event subprocess is **interrupting**:
a cancellation terminates the waiting timer, so the booking cannot also complete.

Call activity mappings (each of the three call activities):

| Direction | Mapping |
|---|---|
| in | `recipientId = if telegramChatId != null then telegramChatId else patientId` |
| in | `messageText =` confirmation / slot-full / cancellation text built from `patientName`, `department`, `preferredSlot`, `bookingRef`, `suggestedAction`, `cancellationReason` |
| out | `notificationStatus` → `confirmationStatus` / `slotFullNoticeStatus` / `cancellationNoticeStatus` |

## Propagate all vs explicit mappings (comparison)

| | Propagate all (`hospital-booking-propagate-all`, P-1004) | Propagation off + mappings (`hospital-booking`, P-1001) |
|---|---|---|
| Child receives | every parent variable: `patientId, patientName, department, preferredSlot, bookedCount, bookingRef, bookingStatus, slotStatus, suggestedAction, appointmentWaitTime` + `recipientId, messageText` (screenshot 12) | only `recipientId`, `messageText` (screenshot 06) |
| Parent gets back | every child variable, under the child's own names: `notificationStatus`, `telegramMessageId` (screenshot 13) | only `confirmationStatus` (renamed via output mapping) |
| Effect | Child is coupled to the parent's variable names, sees patient data it does not need, and its result overwrites the same `notificationStatus` on each call (confirmation then cancellation cannot be told apart). Larger payloads per call. | The child is a real reusable contract (two inputs, one output); each call activity stores its result under its own name; no leakage of patient data. |

Observed while building: Zeebe **ignores `propagateAllChildVariables` when the call activity has output mappings** – the
child's variables then land only in the call activity's local scope. The propagate-all variant therefore has no output mappings.

## Run it

```sh
docker compose up -d --wait            # Operate http://localhost:8088/operate (demo/demo)
npm install
npm run test:api                       # deploy + run the 3 cases + assertions (newman)
npm run screenshots                    # writes Result/*.png
```

Ports 8088 / 26501 / 9601 / 8086 / 8090 are used so this stack can run next to another Camunda on 8080.
Desktop Modeler can deploy to `http://localhost:26501` (no auth).

**Real Telegram:** copy `.env.example` to `.env`, set `TELEGRAM_BOT_TOKEN` and `TELEGRAM_API_BASE=https://api.telegram.org`,
pass the patient's numeric chat id as `telegramChatId` when starting an instance, then `docker compose up -d connectors`.
Note: connectors 8.10 only read secrets from env vars with the `SECRET_` prefix, which the compose file adds.
